# Аналитика образовательной платформы IT Resume

## Цель исследования

Исследовать поведение пользователей корпоративного клиента
образовательной платформы: начало обучения, активность,
успешность попыток решения задач и динамику показателей когорт.

Анализ выполнен на учебной базе данных в рамках обучения
в Simulative для пользователей компании с `company_id = 1`.

## Гипотезы

1. Доля успешных попыток студентов со временем растёт.
2. Снижение активности сопровождается снижением успешности попыток.
3. На платформе есть задачи, вызывающие повышенные затруднения.
4. У отдельных когорт поздняя успешность ниже ранней.
5. Между регистрацией и первыми учебными действиями теряется часть пользователей.

## Подход к анализу

Исследование основано на SQL-анализе учебной базы данных.
Результаты используются для описания поведения пользователей
и формирования бизнес-рекомендаций.

Особенности расчётов и ограничения интерпретации указаны
в соответствующих разделах отчёта.

## 1. Воронка онбординга

[SQL-запрос](../sql/01_onboarding_funnel.sql)

### Метод

Для каждой когорты регистрации подсчитаны зарегистрированные
пользователи и те, кто в том же календарном месяце:

- совершил первую попытку решения задачи;
- впервые успешно решил задачу;
- впервые начал тестирование.

### Наблюдения

Наибольшая потеря пользователей отмечена между регистрацией
и первой попыткой. Среди совершивших первую попытку многие
успешно решали хотя бы одну задачу. До начала тестирования
доходила меньшая часть пользователей.

### Интерпретация

Первый учебный сценарий — приоритетное направление
для дополнительного исследования: необходимо выяснить,
что мешает зарегистрированным пользователям начать обучение.

### Ограничения

Первые действия после месяца регистрации не учитываются.
У пользователей различается время наблюдения до конца месяца.

Начало тестирования не означает его успешного завершения.
Последовательность этапов по времени запросом не проверяется.

## 2. Сложность задач

[SQL-запрос](../sql/02_problem_difficulty.sql)

### Метод

Для задач с числом попыток больше 10 рассчитаны:

- общее число попыток;
- число успешных попыток;
- доля успешных попыток — `success_rate`.

### Наблюдения

Выделены задачи с низкой долей успешных попыток.
Заявленная сложность не всегда соответствовала
наблюдаемой успешности решений.

### Интерпретация

Задачи с низкой успешностью — кандидаты на проверку условий,
объяснений и соответствия учебной программе.

### Ограничения

Низкая успешность сама по себе не доказывает ошибку в задаче:
результат зависит от подготовки студентов и повторных попыток.

Порог больше 10 попыток не гарантирует статистическую
надёжность оценки. Показатель отражает долю успешных попыток,
а не долю студентов, решивших задачу.

## 3. Успешность попыток по месяцам

[SQL-запрос](../sql/03_monthly_success_rate.sql)

### Метод

Для каждого студента рассчитаны число попыток,
число успешных попыток и их доля за каждый месяц с попытками.

### Наблюдения

У студентов отмечены колебания успешности между месяцами:
периоды высоких показателей сменялись снижением и наоборот.

### Интерпретация

Для объяснения изменений необходимо учитывать число попыток,
сложность выбранных задач и этап обучения.

### Ограничения

Доля успешных попыток не является прямой оценкой навыков.
При малом числе попыток показатель может быть нестабильным.

Месяцы без попыток в результат не входят.

## 4. Динамика успешности

[SQL-запрос](../sql/04_success_rate_dynamics.sql)

### Метод

С помощью оконной функции `LAG` успешность каждого студента
сравнивается с предыдущим месяцем, в котором были попытки.

Выделены периоды роста, снижения и отсутствия изменений.

### Наблюдения

Отмечены чередования роста и снижения показателя.
Устойчивый рост не был общим для всех студентов.

### Интерпретация

Результат помогает находить периоды изменения успешности
для дальнейшего изучения учебной траектории студента.

### Ограничения

Месяцы без попыток пропускаются. Поэтому сравнение может
охватывать промежуток больше одного календарного месяца.

Доли сравниваются после округления до двух знаков:
небольшие изменения могут классифицироваться как отсутствие
изменений.

Рост или снижение показателя не доказывает изменение
качества обучения.

## 5. Динамика активности

[SQL-запрос](../sql/05_activity_dynamics.sql)

### Метод

Число попыток каждого студента сравнивается с предыдущим
месяцем с попытками с помощью функции `LAG`.

### Наблюдения

Активность менялась неравномерно: периоды роста
могли сменяться снижением числа попыток.

### Интерпретация

Расчёт позволяет выделять изменения интенсивности работы
с задачами и выбирать периоды для дополнительного анализа.

### Ограничения

Месяцы без попыток отсутствуют в результате.
Полное прекращение активности не отражается как падение до нуля.

Большее число попыток может означать как вовлечённость,
так и затруднения при решении.

## 6. Когортный анализ

[SQL-запрос](../sql/06_cohort_analysis.sql)

### Метод

Пользователи объединены в когорты по месяцу регистрации.

Для каждого месяца жизни когорты рассчитано отношение
суммарных успешных попыток к суммарным попыткам.

Сопоставлены два показателя:

- `early_rate` — среднее доступных месячных долей
  для возрастов когорты 0 и 1;
- `late_rate` — доля успешных попыток
  в последнем месяце с попытками.

Разница между поздним и ранним показателями отражает
направление изменения.

### Наблюдения

У ряда когорт поздняя успешность была ниже ранней.
Встречались также когорты с ростом показателя.

### Интерпретация

Когорты со снижением показателя требуют дополнительного
изучения: изменения могут быть связаны со сложностью задач,
составом активных студентов и этапом обучения.

### Ограничения

Месячный показатель когорты взвешен числом попыток:
студенты с большим числом попыток сильнее влияют на результат.

При расчёте раннего среднего месяцы имеют одинаковый вес,
независимо от числа попыток.

У молодых когорт ранний и поздний периоды могут пересекаться.
Последний месяц наблюдения может быть неполным,
а состав активных студентов — меняться.

В итоговой классификации отдельно учитываются рост,
снижение, отсутствие изменений и отсутствие данных
для сравнения.

## 7. Сегментация студентов

[SQL-запрос](../sql/07_student_segmentation.sql)

### Метод

Для каждого студента за месяц рассчитаны:

- число попыток;
- число активных дней;
- доля успешных попыток;
- средняя сложность задач по попыткам;
- изменение успешности и средней сложности.

Активный день — календарный день хотя бы с одной попыткой.

Порог сегментации — медиана числа активных дней
по всем парам «пользователь — месяц» с попытками.

Если активных дней меньше медианы, присваивается
сегмент `low_activity`, иначе — `normal_activity`.

### Результат

Сформированы сегменты активности и показатели для последующего
сравнения поведения студентов.

### Интерпретация

Сегментация позволяет выделить пользователей с относительно
низкой активностью и исследовать потребность
в дополнительной поддержке.

### Ограничения

Общий медианный порог не учитывает сезонность и различия
в длительности наблюдения.

Средняя сложность рассчитана по попыткам, включая повторные,
а не по уникальным задачам.

Изменения показателей сравниваются с предыдущим месяцем
с попытками.

Низкая активность не доказывает низкую мотивацию,
риск ухода или ухудшение навыков.

## Оценка гипотез

| Гипотеза | Результат |
| --- | --- |
| Успешность студентов растёт со временем | Однозначного подтверждения нет: наблюдались разнонаправленные изменения |
| Снижение активности сопровождается снижением успешности | Требует отдельного количественного сравнения; представленные расчёты не дают достаточного подтверждения |
| Есть задачи, вызывающие повышенные затруднения | Выделены кандидаты по низкой доле успешных попыток; причины требуют проверки |
| У отдельных когорт поздняя успешность ниже ранней | Такое снижение отмечено, но сопоставимость периодов ограничена |
| Между регистрацией и первыми действиями теряется часть пользователей | Наблюдение относится к первым действиям в календарном месяце регистрации |

Исследование носит описательный характер.
Статистические тесты в представленных запросах не выполняются.
Наблюдаемые связи не доказывают причинность.

## Бизнес-рекомендации

### Улучшить начало обучения

Изучить причины отсутствия первой попытки после регистрации.
Проверить более понятный стартовый сценарий и вводное задание.

### Провести аудит задач

Проверить задачи с низкой долей успешных попыток:
условия, подсказки, необходимые знания и место в программе.

### Поддерживать регулярность обучения

Проверить напоминания и небольшие регулярные задания.
Оценивать результат по активным дням и возвращаемости,
учитывая успешность попыток.

### Исследовать разные учебные траектории

Проверить необходимость разных последовательностей задач
и темпов прохождения для студентов с разной подготовкой.

### Изучить снижение активности

Определить периоды снижения активности и проверить
сценарии возвращения к обучению.

Рекомендации являются предложениями для дальнейшей проверки.
Их внедрение и влияние на показатели в рамках проекта
не оценивались.
